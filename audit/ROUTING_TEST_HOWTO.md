# 발화 라우팅을 테스트하는 방법 — 세 번 다르게 재보고 얻은 것

라우팅(`rankTopics`·`SEARCH_SYNONYMS`)을 건드릴 때 참고용입니다. **규칙이 아니라 관찰 기록**입니다.
2026-09-07에 같은 사안을 세 가지 방식으로 재봤더니 결론이 뒤집혀서, 어떻게 재는 게 나은지 정리했습니다.

원자료: `audit/UTTERANCE_TEST_0905.md`

---

## 요약

같은 25개 사안을 입력 형태만 바꿔 넣었습니다.

| 입력 형태 | 정답 | 0건 | 오답 |
|---|---|---|---|
| 게시판 글 제목 | 9 | **16** | 0 |
| 사람이 카톡에 칠 말 | **14** | 9 | 2 |
| 그것을 LLM이 요약한 문장 (실사용 경로) | 12 | 5 | **8** |

세 줄이 전부 다릅니다. **어떻게 재느냐에 따라 "잘 되고 있다"와 "심각하다"가 갈립니다.**

## 1. 게시판 제목을 그대로 넣으면 비관적으로 나옵니다

처음에 네이버 카페 글 제목 202개·195개를 그대로 `search_topics`에 넣어 쟀습니다. 0건이 21~27% 나왔습니다.

그런데 게시판 제목은 사람이 상담창에 치는 말이 아닙니다.

```
게시판 제목:   "[개인]수정조정신청하려면..."
카톡에 칠 말:  "채무조정 받고 있는데 조건을 바꾸고 싶어요"
```

`[개인]` 같은 말머리, 말줄임표, 명사형 종결은 게시판 문법입니다. 축약돼 있어서 매칭이 덜 되고, **0건이 실제보다 부풀려집니다.** 위 표에서 제목은 0건 16개인데 카톡 발화는 9개였습니다.

동시에 **오답은 과소평가됩니다.** 제목에는 범용어가 없어서 노이즈 매칭이 잘 안 일어납니다(제목 기준 오답 0개).

## 2. 실사용은 한 단계가 더 있습니다 — LLM 요약

```
사용자가 카톡에 씀  →  호스트 LLM이 요약  →  triage(situation)
```

`triage`의 inputSchema가 이렇게 지시합니다.

> 사용자의 발화 원문을 그대로 넣지 말고, 이름·연락처 등 개인정보를 제외하고 **문제 유형 중심으로 요약해 전달하세요.**

개인정보를 빼려는 의도는 옳습니다. 다만 그 요약에 `문의`·`대응`·`방법`·`심사`·`처리` 같은 **범용 명사가 새로 붙습니다.** 이 말들이 여러 주제 제목에 들어 있어 제목 매칭(+4)을 받습니다.

실제로 관측된 것:

| 카톡에 친 말 | 그 결과 | LLM 요약 | 그 결과 |
|---|---|---|---|
| 주부인데 개인워크아웃 신청할 수 있나요 | 신용회복위원회채무조정 ✅ | 무직 주부의 개인워크아웃 신청 자격 **문의** | **체류기간연장변경** ❌ |
| 대부업체 빚도 채무조정 되나요 | 신용회복위원회채무조정 ✅ | 대부업체 채무 조정 가능 여부 **문의** | **새출발기금** ❌ |
| 개인회생 다시 신청할 수 있나요 | 개인회생 ✅ | 재회생 **신청** 가능 여부 **문의** | **재정신청** ❌ |
| 소득이 적은데 부양가족 넣어야 하나요 | (0건) | 채무조정 **심사** 시 부양가족 반영 **문의** | **정신질환_비자의입원_심사** ❌ |
| 법원에서 보정명령 왔는데 뭘 해야해요 | 소장받았을때 ✅ | 법원에서 보정명령을 받았고 **대응 방법**을 알고 싶음 | **렌터카사고분쟁** ❌ |

마지막 줄은 실사용 대화에서 그대로 나온 것입니다.

**제안**: `triage`를 테스트할 때는 원문만 넣지 말고, 호스트 LLM이 요약할 법한 문장으로도 한 번 넣어봅니다. 요약문은 대체로 명사형으로 끝나고 `문의`·`대응`·`방법`으로 마무리됩니다.

## 3. 0건 개수는 지표로 쓰기 어렵습니다

0건을 줄이는 가장 쉬운 방법이 "아무 데나 보내기"입니다. 그래서 0건만 보면 개선처럼 보입니다.

실제로 `hay`(점수 계산 대상 문자열)에 `단계`·`비고` 필드를 추가하는 실험을 했습니다.

```
0건        52 → 46   (6개 줄어듦)
기존 테스트  244개 전부 통과
실제 변화   13개 중 8개가 나빠짐
```

나빠진 것:
```
(0건)    → 압수수색적법성       성질 못 참고 화를 표시하게되면
(0건)    → 공무원불친절부당대우   신속 실효 중에 햇살론 카드 쓸 수 있나요?
(0건)    → 대출빙자형          신용회복중입니다. 완제 후 대출 문의
새출발기금  → 국가장학금_학자금대출  새출발 부실우려 진행중인데 추가 대출
개인회생   → 불법추심대응        [회생]금지명령 안나왔는데
```

**제안**: 정답 / 0건 / 오답 **셋으로 나눠 셉니다.** 0건은 "찾지 못했습니다"라는 무응답이고, 오답은 틀린 절차로 보내는 오안내입니다. 성격이 다릅니다.

## 4. `npm test` 통과가 안전을 보장하지는 않았습니다

위 실험에서 **244개가 전부 통과했는데 8건이 나빠졌습니다.** 기존 테스트는 이미 알고 있는 케이스를 지키는 것이라, 처음 보는 발화에서 생기는 회귀는 잡지 못합니다.

**제안**: 라우팅을 바꿨으면 실사용 발화 세트로 **변경 전후 1순위를 하나씩 비교(diff)** 합니다. 총계만 보면 좋아진 것과 나빠진 것이 상쇄되어 안 보입니다. 위 실험도 총계로는 개선이었습니다.

```
# 전후 비교의 최소 형태
변경 전 결과를 JSON으로 저장 → 코드 수정 → 같은 입력으로 다시 → 1순위가 달라진 것만 출력
```

## 5. 넓히는 변경에는 네거티브를 같이 겁니다

동의어를 넓히면 무관한 발화가 딸려옵니다. `명도`·`압류방어` 같은 넓은 말을 넣었을 때 게시판 잡담이 함께 매칭됐습니다.

`test/server.test.ts`에 이미 그런 테스트가 있습니다(스토킹 네거티브, 카페 후기 네거티브). 넓히는 변경마다 "이건 이 주제로 가면 안 된다"를 같이 추가하면 좋겠습니다.

다만 **모든 오매칭을 막을 필요는 없습니다.** `서울 서부 명도 완료 타임라인`은 이제 매칭되지만 상담창에 칠 문장이 아니라 실해가 없습니다. 이걸 막으려면 `명도`를 좁혀야 하고, 그러면 `명도일이 걱정이에요`가 죽습니다. 판단 기준은 **"카톡 입력창에 사람이 실제로 칠 법한 문장인가"** 로 잡았습니다.

## 6. 커뮤니티 글로 검증할 때

이 레포는 공개 저장소입니다. 네이버 카페 글로 검증하면서 **다른 회원의 닉네임이 포함된 제목이 커밋된 적이 있습니다**(이후 제거). 본문은 개인 사연이라 더 민감합니다.

수집 스크립트의 방침은 `scripts/NAVER_CAFE_SCRAPER.md`에 있습니다 — 수집물은 `.gitignore` 대상이고, 주제·동의어 데이터에 원문을 넣지 않습니다.

**제안**: 테스트에 넣을 때도 원문 그대로보다 표현 패턴만 가져와 다시 쓰는 편이 안전합니다. 어차피 게시판 제목은 위 1번 이유로 실사용과 다르므로, 카톡 말투로 바꿔 쓰는 것이 검증 정확도에도 낫습니다.

### 수집 시 정렬 기준

좋아요순으로 뽑으면 **정보공유·후기·팁만 올라옵니다.** 질문글에는 좋아요가 붙지 않습니다.

```
좋아요순 202개 → 좋아요 중앙값 11 · 최대 839 · 0인 글 3개
최신순  195개 → 좋아요 중앙값  0 · 최대  14 · 0인 글 131개
```

스크래퍼 기본값을 최신순으로 바꿨습니다(`python collect_ccrs5500_top.py 50 RECENT out.json`).

**게시판 제목으로 재면 0건이 부풀고 오답이 숨습니다. 실사용 경로(LLM 요약)로 재면 오답이 드러납니다. 0건만 보지 말고 정답·0건·오답 셋으로 세고, 바꾸기 전후를 하나씩 비교합니다.**
